# Схеми даних REST API

Джерела: [SRS](../spec/srs.md), [REQ](../spec/functional-requirements.md), [глосарій](../spec/glossary.md), [AC](../spec/acceptance-criteria.md), [BDD](../spec/bdd-scenarios.md). Схеми деталізують [ресурси](resources.md), [операції](operations.md) та [запити й відповіді](requests-responses.md); усі маршрути з префіксом `/api/v1` збережено. Це Markdown-опис контракту, без OpenAPI або реалізації.

У таблицях «так» означає обов’язкову наявність поля; `null` дозволено лише явно. Усі об’єкти запитів закриті: невідомі поля відхиляються з 422. Довільні ключі дозволені лише всередині `characteristics`. У PATCH кожне дозволене поле необов’язкове, але потрібне щонайменше одне; передане `characteristics` замінює весь об’єкт. Поля відповідей не стають автоматично дозволеними полями запису. Спільні типи та вкладені схеми застосовуються без зміни назв JSON-полів.

Схема ErrorResponse та вкладена FieldError визначені в [єдиній моделі помилок](error-model.md), без дублювання тут. Для PRICE_CHANGED модель використовує схему Quote з цього документа; токен підтвердження ціни відрізняється від токена сесії.

## Спільні типи

У цій таблиці «поле» позначає назву повторно використовуваного типу; обов’язковість його використання визначається схемою об’єкта.

| Поле / тип | Тип JSON | Обов’язковість | Обмеження / опис |
| --- | --- | --- | --- |
| Id | string | За схемою | Непорожній непрозорий рядок для id, carId, bookingId, periodId, clientId, accountId, authorAccountId; без припущень про UUID чи числовий формат |
| Token | string | За схемою | Непорожній непрозорий рядок; accessToken або priceConfirmationToken |
| NonEmptyString | string | За схемою | Щонайменше один непробільний символ; порожній рядок і рядок лише з пробільних символів заборонені; для імен, телефону, причин, назв і значень характеристик; без довільної максимальної довжини чи regex телефону |
| Email | string | За схемою | Формат email після видалення крайніх пробілів; зіставлення й перевірка унікальності без регістру за REQ-F-010, REQ-F-011, REQ-F-013; примусове зниження регістру збереженого значення не вимагається |
| NewPassword | string | За схемою | Від 8 символів; пробіли не обрізаються; тільки вхідне поле |
| LocalHour | string | За схемою | Структура YYYY-MM-DDTHH, наприклад 2026-11-12T09; чотири цифри року, місяць 01–12, день 01–31, година 00–23; хвилини й секунди не передаються, дорівнюють 00; без зміщення. Існування календарної дати й коректність часу перевіряє сервер |
| EventTime | string | За схемою | RFC 3339 із відомим зміщенням UTC, наприклад 2026-11-12T09:15:00+02:00; точність до години не вимагається |
| Timezone | string | За схемою | Лише Europe/Kyiv, також для службових періодів |
| Money | string | За схемою | Десятковий запис із двома знаками після крапки, наприклад 1250.00; не JSON number, без експоненти; без довільної верхньої межі |
| DailyRate | Money | За схемою | Числове значення > 0; перевірка точної десяткової величини, без перетворення у двійковий float |
| Currency | string | За схемою | Лише UAH |
| BillableDays | integer | За схемою | Від 1 до 30 включно |
| FutureBookingsCount | integer | За схемою | ≥ 0 |
| BookingStatus | string | За схемою | confirmed, active, completed, cancelled |
| AccountRole | string | За схемою | client або administrator |
| Characteristics | object | За схемою | Щонайменше одна пара; кожна назва й кожне значення — NonEmptyString; масиви, числа, null і вкладені об’єкти як значення не дозволені |

Для LocalHour схема перевіряє структуру рядка та діапазони компонентів. Сервер додатково перевіряє існування календарної дати (наприклад, 30 лютого відхиляється) і коректність часу в Europe/Kyiv: неіснуючі та неоднозначні місцеві межі відхиляються, зокрема для службових періодів. Самого шаблону рядка для цих перевірок недостатньо. Для Email нормалізація передує перевірці формату; перевірка зайнятості адреси є бізнес-перевіркою. NonEmptyString не вимагає обрізання: перевіряється наявність непробільного символу в початковому значенні. Це правило не застосовується до паролів; паролі не змінюються й не обрізаються.

### ClientCancellation — представлення скасування для клієнта, також відповідь OP-13

«Клієнтське представлення» означає одержувача даних: authorRole може бути administrator, якщо скасування виконав адміністратор.

| authorRole | AccountRole | Так | Роль автора, визначена сервером |

Принаймні одне поле. carId задає шлях; id, carId, timezone у тілі не приймаються. Сервер перевіряє підсумковий період після застосування PATCH. Цілі години та відхилення проблемного місцевого часу застосовуються, обмеження оренди 1–30 діб і 90 днів — ні.

## Обгортки списків

Кожна названа схема має одне обов’язкове поле items. Порожні масиви дозволені; null заборонено; пагінації, сортування й додаткових полів немає.

| Схема / поле | Тип | Обов’язковість | Обмеження / опис |
| --- | --- | --- | --- |
| PublicCarList.items | array<PublicCar> | Так | OP-01 для гостя/клієнта |
| AdminCarList.items | array<AdminCar> | Так | OP-01 для А; OP-14 |
| ClientBookingList.items | array<ClientBooking> | Так | OP-11 для К, лише власні |
| AdminBookingList.items | array<AdminBooking> | Так | OP-11 для А, усі |
| ServicePeriodList.items | array<ServicePeriod> | Так | OP-18; майбутні та історичні |

## Межа схеми й бізнес-перевірок

| Рівень | Перевірки |
| --- | --- |
| Схема | Типи, обов’язковість, null, наявність непробільного символу для NonEmptyString, формат email після нормалізації, довжина нового пароля, структура characteristics, десятковий формат і додатність тарифу, цілі числові межі, enum, структура рядка й діапазони компонентів LocalHour, формат EventTime, закриті запити та непорожній PATCH |
| Залежності полів у схемі | Пара меж CatalogQuery; reason залежно від authorRole; cancellation залежно від status |
| Застосування PATCH | characteristics замінюється повністю; пропущені поля лишаються незмінними; підсумковий об’єкт проходить бізнес-перевірки |
| Часові бізнес-перевірки | Існування календарної дати та коректність часу в Europe/Kyiv, зокрема існування й однозначність введених меж; endsAt > startsAt; поточний час, автоматичні стани, межа скасування; для OP-09/OP-10 — майбутній початок, 1–30 календарних діб і горизонт 90 днів |
| Службові періоди | Майбутній початок при створенні та в результаті редагування; редагування/видалення лише до чинного початку; відсутність лімітів оренди 1–30/90; історія після початку |
| Доступність і конкурентність | Перетини напіввідкритих періодів, приховування, атомарне резервування й службові зміни; суміжність дозволена; скасований запис не блокує період |
| Вартість | Календарні обчислення billableDays, totalPrice = dailyRate × billableDays, незмінність зафіксованих сум; чинність токена, актуальність версії тарифу й повторне підтвердження |
| Облікові записи | Унікальність нормалізованої пошти, перевірка поточного пароля, лічильники невдалих входів і блокування |
| Права й приватність | Роль, власність, належність periodId до carId; вибір публічного/адміністративного представлення; заборона створення бронювання А; відсутність секретів і службових причин у недозволених відповідях |

Для пошуку OP-01/OP-03 застосовуються порядок і валідність часових меж, але не майбутність, тривалість 1–30 діб і горизонт 90 днів. Історичні представлення також не перевіряються на майбутність. Повна заміна characteristics — правило застосування PATCH, а не злиття вкладених полів.

## Погоджені проєктні уточнення та відкриті питання

Рішення надано користувачем у поточному завданні. Нижче збережено зв’язок із REQ/AC у дусі [CP-01](../planning/revised-decomposition.md); це уточнення API, без зміни вихідних REQ-ID, SRS чи позначення Gate як пройдених.

| Уточнення | Зв’язок із вимогами та прийнятими перевірками |
| --- | --- |
| dailyRate > 0, два десяткові знаки, без довільної верхньої межі | Проєктне бізнес-уточнення Q-04 / SR-005; REQ-F-037, REQ-F-065, REQ-F-067; AC-F-037-01, AC-F-065-01, AC-F-067-01. Нуль, від’ємні й дроби менш ніж копійка відхиляються, не округлюються мовчки |
| characteristics — непорожній словник непорожніх рядків | Проєктне уточнення Q-02 / SR-002; REQ-F-002, REQ-F-065–REQ-F-066; AC-F-002-01, AC-F-065-01, AC-F-066-01. Фіксований перелік характеристик не вводиться |
| Службові межі в Europe/Kyiv, YYYY-MM-DDTHH; проблемний час відхиляється | Проєктне бізнес-уточнення Q-06 / SR-006; REQ-F-073–REQ-F-075; AC-F-073-01–AC-F-075-01. Без перенесення лімітів оренди 1–30/90 |
| Непорожні значення, формат email, закриті запити й правила PATCH | Погоджена деталізація контракту для REQ-F-009, REQ-F-014, REQ-F-021, REQ-F-058, REQ-F-066, REQ-F-074–REQ-F-075; нових максимальних довжин, regex телефону або ролей немає |

Відкритими залишаються строк дії сесії та наслідки зміни пароля для чинних сесій. Окреме календарне питання Q-07 залишається відкритим: як обчислювати проміжні добові межі й 90-денний горизонт, якщо обчислений місцевий час повторюється або не існує. Відхилення введених меж і спеціальне правило межі скасування не розв’язують це питання автоматично.
