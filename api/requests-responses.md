# Запити й відповіді REST API

Погоджені уточнення: [ADD-001](../spec/srs-addendum-001.md), REQ-F-093–REQ-F-096 та додаткові AC календарних вимог. Сесія чинна рівно 86 400 секунд від входу, без автоматичного продовження. Від точної межі або після успішної зміни пароля старий токен дає 401 AUTHENTICATION_REQUIRED з WWW-Authenticate: Bearer. Успішна зміна пароля повертає 204 без тіла й анулює всі сесії цього запису, включно з поточною; наступний захищений запит вимагає повторного входу. Невдала зміна не анулює сесій, якщо їх початковий строк ще не завершився. За ADD-001 кожну обчислену календарну межу визначають від початкової місцевої опори Europe/Kyiv: неіснуючу переносять вперед на величину переходу, для неоднозначної вибирають пізніший момент. Перенесення не накопичуються. Це діє для меж 1/30 діб, оплачуваних діб та горизонту 90 днів; введені проблемні години як і раніше відхиляються з 422, правило дедлайну скасування збережено.


Контракт деталізує [операції](operations.md) та [ресурси](resources.md), узгоджені з [вимогами](requirements.md). Усі наведені формати, назви полів, HTTP-коди й механізм сесії — **проєктні рішення**, а не нові вимоги SRS. Префікс усіх URI — `/api/v1`.

Типи, обов’язковість, null і погоджені проєктні уточнення визначено в [схемах даних](data-schemas.md). Вони відокремлюють перевірку форми даних від бізнес-перевірок.

Для імен, телефону, причин, назв і значень характеристик «непорожній рядок» означає щонайменше один непробільний символ; обрізання не вимагається. Це правило не застосовується до паролів: вони не змінюються й не обрізаються. Для LocalHour схема перевіряє структуру рядка та діапазони компонентів, а сервер додатково — існування календарної дати й коректність часу в Europe/Kyiv; самого шаблону недостатньо.

## Спільні домовленості

| Елемент | Контракт |
| --- | --- |
| Формат | HTTPS; JSON для тіл запитів і відповідей, крім порожньої відповіді 204 |
| Ідентифікатори | carId, bookingId, periodId, clientId, accountId — непорожні непрозорі рядки; створює сервер; токени також непорожні непрозорі рядки |
| Вхідні поля | Обов’язкові, якщо не зазначено «необов’язкове»; невідомі поля відхиляються з 422; PATCH містить хоча б одне дозволене поле |
| Період | startsAt, endsAt — місцеві рядки YYYY-MM-DDTHH без зміщення; хвилини й секунди не передаються та дорівнюють 00; endsAt > startsAt; timezone = Europe/Kyiv, також для службових періодів; неіснуючий і неоднозначний час відхиляються |
| Розрахунок і бронювання (OP-09, OP-10) | Коректні дати; хвилини 00; неоднозначні й неіснуючі межі відхиляються; початок > зараз і ≤ зараз + 90 календарних днів; 1–30 календарних діб |
| Пошук і доступність (OP-01, OP-03) | Коректні дати, endsAt > startsAt, хвилини 00; неоднозначні й неіснуючі межі в Europe/Kyiv відхиляються. Обмеження майбутнього початку, тривалості 1–30 діб і горизонту 90 днів не застосовуються |
| Час події | cancelledAt, clientCancellationDeadline — RFC 3339 зі зміщенням, яке однозначно визначає момент; поле timezone задає календарний контекст |
| Перетини | Напіввідкриті інтервали [startsAt, endsAt); суміжність дозволена; перевірки запису атомарні також щодо паралельної службової недоступності |
| Гроші | dailyRate, totalPrice — десяткові рядки з двома знаками, dailyRate > 0, currency = UAH; сервер обчислює ціну без двійкової похибки; верхню межу не встановлено; додатність тарифу — погоджене проєктне уточнення |
| Автентифікація | OP-05 повертає непрозорий accessToken; захищені запити: Authorization: Bearer <accessToken>; строк дії — рівно 24 години від входу, без продовження |
| Колекції | Об’єкт {items: [...]} без пагінації, сортування й додаткових фільтрів; порожній результат — items: [] |
| Створення | 201; Location для адресованого ресурсу (авто, бронювання, скасування, службовий період); реєстрація клієнта — без Location, із даними створеного клієнта та без автоматичного входу |

Публічна реєстрація не виконує автоматичного входу. Паролі, їх хеші, лічильники помилок і засіб автентифікації не входять до представлень профілю чи бронювань.

## Склад представлень

| Назва | Поля успішної відповіді |
| --- | --- |
| Car | id, characteristics (об’єкт рядкових характеристик), dailyRate, currency; для А також hidden (boolean), futureBookingsCount (ціле ≥ 0) |
| Profile | clientId, firstName, lastName, email, phone; імена й телефон — непорожні рядки; email — формат email з нормалізацією за SRS |
| Quote | carId, startsAt, endsAt, timezone, dailyRate, billableDays (ціле 1–30), totalPrice, currency, priceConfirmationToken |
| Booking | id, car: {id, characteristics}, startsAt, endsAt, timezone, status, dailyRate, billableDays, totalPrice, currency, clientCancellationDeadline, cancellation |
| Booking для А | Усі поля Booking та client: {clientId, firstName, lastName, email, phone} з актуального профілю |
| Cancellation | cancelledAt, authorRole (client або administrator), reason (непорожній рядок для адміністративного скасування; для клієнтського null); лише для А також authorAccountId; усі дозволені поля обов’язково присутні |
| ServicePeriod | id, carId, startsAt, endsAt, timezone, reason; усі поля зберігаються після початку |

`futureBookingsCount` — кількість підтверджених бронювань авто з початком строго після поточного серверного часу; скасовані, активні й завершені не враховуються. Поле лише для читання в усіх адміністративних представленнях Car (OP-01, OP-02, OP-14–OP-16), у публічних відповідях відсутнє. OP-02 та OP-14 дозволяють показати попередження перед приховуванням. Лічильник актуальний на момент відповіді; PATCH повторно визначає його для попередження. Передавання futureBookingsCount у POST/PATCH відхиляється з 422.

У Booking `cancellation` обов’язково присутнє й дорівнює null до скасування; після скасування — об’єкт. billableDays — ціле 1–30. `status`: confirmed, active, completed, cancelled. Нескасоване бронювання активне від початку включно до завершення невключно; завершене від завершення включно. Представлення завжди відображає актуальний стан незалежно від способу реалізації переходів.

Проєктно `characteristics` містить щонайменше одну непорожню пару «назва: значення»; фіксований перелік характеристик SRS не задає. У бронюванні достатньо зв’язку з конкретним авто та його поточних характеристик: SRS не вимагає їх знімка. Навіть приховане авто лишається у власному бронюванні. Дані автора-адміністратора клієнту не повертаються, включно з ідентифікатором. Службові причини відсутні в будь-якій публічній відповіді, навіть помилковій.

## Реєстрація, вхід і профіль

| OP / метод і URI після префікса | Шлях | Query | Тіло | Успішна відповідь | HTTP-коди помилок |
| --- | --- | --- | --- | --- | --- |
| OP-04 POST /clients | — | — | firstName, lastName, email, phone, password — рядки | 201 {profile: Profile, role: client}; без Location та автоматичного входу | 400; 409 — пошта зайнята; 422 |
| OP-05 POST /sessions | — | — | email, password — рядки | 201 {accessToken, tokenType: Bearer, accountId, role: client/administrator} | 400; 401 — невірні дані; 422 — відсутні поля; 429 — тимчасове блокування |
| OP-06 GET /profile | — | — | — | 200 Profile | 401; 403 |
| OP-07 PATCH /profile | — | — | firstName, lastName, phone — кожне необов’язкове | 200 Profile | 400; 401; 403; 422 — також спроба передати email, clientId або role |
| OP-08 PUT /profile/password | — | — | currentPassword, newPassword — рядки | 204, без тіла | 400; 401; 403; 422 — поточний пароль невірний або новий коротший за 8 символів |

Пошта обрізається по краях перед перевіркою формату email й порівнюється без регістру. Імена, телефон і причини — непорожні рядки; максимальні довжини й regex телефону не встановлюються. Новий пароль — від 8 символів, без обрізання пробілів; пароль входу й поточний пароль також не обрізаються. Для OP-05 п’ята послідовна помилка вже повертає 429; відповідь містить error.code = LOGIN_BLOCKED та Retry-After у секундах до початкової межі 15 хвилин. Повторні спроби не подовжують цю межу; успішний вхід або сплив строку скидають лічильник.

## Розрахунок і створення бронювання

| OP / метод і URI після префікса | Шлях | Query | Тіло | Успішна відповідь | HTTP-коди помилок |
| --- | --- | --- | --- | --- | --- |
| OP-09 POST /booking-quotes | — | — | carId, startsAt, endsAt | 200 Quote; запис бронювання не виникає | 400; 401; 403; 404; 409 — авто недоступне; 422 |
| OP-10 POST /bookings | — | — | carId, startsAt, endsAt, priceConfirmationToken | 201 Booking зі status=confirmed | 400; 401; 403 — також роль А; 404; 409 — недоступність або зміна тарифу; 422 |

**Проєктне підтвердження ціни:** сервер видає захищений від підроблення `priceConfirmationToken`, пов’язаний із клієнтом, авто, періодом, показаними тарифом, сумою й версією тарифу. Клієнт передає його лише після підтвердження показаної суми. Токен не резервує авто й не фіксує ціну наперед; clientId, status, dailyRate і totalPrice у тілі OP-10 заборонені.

При OP-10 сервер повторно й атомарно перевіряє період, приховування, перетини та версію тарифу. Невалідний токен або невідповідність його авто, клієнта чи періоду — 422. Змінений тариф — 409 PRICE_CHANGED з `error.details.quote: Quote`, який містить оновлені тариф, суму та новий токен; бронювання не створюється. Після повторного підтвердження клієнт повторює OP-10 з новим токеном. Перевірка версії виявляє також зміну тарифу й повернення до попереднього значення. Втрата доступності — 409 CAR_UNAVAILABLE, без подробиць чужих бронювань чи службової причини.

Кількість оплачуваних календарних діб і сума розраховуються сервером; вони фіксуються тільки при успішному створенні. Окремого резервування під час розрахунку, ручного підтвердження або зміни створеного бронювання немає.

## Перегляд і скасування бронювань

| OP / метод і URI після префікса | Шлях | Query | Тіло | Успішна відповідь | HTTP-коди помилок |
| --- | --- | --- | --- | --- | --- |
| OP-11 GET /bookings | — | — | — | 200 {items: Booking[]}; К — власні; А — усі з client | 401; 403 |
| OP-12 GET /bookings/{bookingId} | bookingId | — | — | 200 Booking відповідної ролі | 400; 401; 403; 404 — немає або чуже для К |
| OP-13 POST /bookings/{bookingId}/cancellation | bookingId | — | К: {} або без тіла; А: {reason: непорожній рядок} | 201 Cancellation відповідної ролі; бронювання стає cancelled | 400; 401; 403; 404 — немає або чуже для К; 409 — стан чи строк; 422 — причина А відсутня/порожня |

Клієнтська причина проєктно не приймається: SRS не вимагає її збереження. Автор, роль і час визначаються сервером. Повторне скасування проєктно повертає 409 ALREADY_CANCELLED без нового запису. Для К після межі — 409 CANCELLATION_DEADLINE_PASSED; для обох ролей від початку оренди — 409 BOOKING_NOT_CANCELLABLE.

`clientCancellationDeadline` обчислюється як той самий місцевий час попередньої доби; неіснуючий переноситься вперед на величину зсуву, повторюваний — у пізніше входження. Клієнт може скасувати рівно на межі включно; А — тільки строго до початку. Перевірка часу, зміна стану, запис автора й звільнення періоду виконуються атомарно. Історія читається через OP-11/OP-12 постійно.

## Керування автопарком

| OP / метод і URI після префікса | Шлях | Query | Тіло | Успішна відповідь | HTTP-коди помилок |
| --- | --- | --- | --- | --- | --- |
| OP-14 GET /admin/cars | — | — | — | 200 {items: Car[]} включно з прихованими | 401; 403 |
| OP-15 POST /cars | — | — | characteristics, dailyRate; hidden — необов’язкове boolean, типово false | 201 Car для А | 400; 401; 403; 422 |
| OP-16 PATCH /cars/{carId} | carId | — | characteristics, dailyRate, hidden — кожне необов’язкове | 200 {car: Car, warnings: [{code, futureBookingsCount}]} | 400; 401; 403; 404; 422 |
| OP-17 DELETE /cars/{carId} | carId | — | — | 204, без тіла | 400; 401; 403; 404; 409 — є будь-який пов’язаний запис |

У PATCH `characteristics` проєктно замінює весь об’єкт характеристик. При переході hidden=false → true, якщо є майбутні підтверджені бронювання, warnings містить code=FUTURE_BOOKINGS_EXIST і їх кількість; інакше масив порожній. Попередження не блокує приховування, яке не скасовує бронювань. Повернення hidden=false зберігає службові періоди. Зміна тарифу не впливає на зафіксовані суми бронювань. OP-17 перевіряє також скасовані бронювання та історичні службові періоди.

## Службова недоступність

| OP / метод і URI після префікса | Шлях | Query | Тіло | Успішна відповідь | HTTP-коди помилок |
| --- | --- | --- | --- | --- | --- |
| OP-18 GET /cars/{carId}/service-unavailabilities | carId | — | — | 200 {items: ServicePeriod[]} | 400; 401; 403; 404 |
| OP-19 GET /cars/{carId}/service-unavailabilities/{periodId} | carId, periodId | — | — | 200 ServicePeriod | 400; 401; 403; 404 |
| OP-20 POST /cars/{carId}/service-unavailabilities | carId | — | startsAt, endsAt, reason | 201 ServicePeriod | 400; 401; 403; 404; 409 — перетин; 422 — поля чи час |
| OP-21 PATCH /cars/{carId}/service-unavailabilities/{periodId} | carId, periodId | — | startsAt, endsAt, reason — кожне необов’язкове | 200 ServicePeriod | 400; 401; 403; 404; 409 — вже почався або перетин; 422 |
| OP-22 DELETE /cars/{carId}/service-unavailabilities/{periodId} | carId, periodId | — | — | 204, без тіла | 400; 401; 403; 404; 409 — вже почався |

Лише А. Належність periodId саме carId перевіряється; невідповідність — 404. На момент PATCH чинний період ще не почався; запропонований початок також має бути в майбутньому. Перетини з підтвердженими/активними бронюваннями й іншими службовими періодами перевіряються атомарно; редагований запис не конфліктує із собою. Конфлікт не скасовує бронювання. Від початку включно PATCH і DELETE заборонені; GET зберігає історію.

**Погоджене проєктне уточнення:** службові межі мають формат YYYY-MM-DDTHH у Europe/Kyiv, хвилини 00; неіснуючий і неоднозначний час відхиляються. Обмеження оренди 1–30 діб і 90 днів до службових періодів не застосовуються. Схема перевіряє форму полів; сервер окремо перевіряє часову зону, порядок меж, майбутній початок і перетини.

## Єдина модель помилок

Структура, обов’язковість полів, відповідність HTTP-статусів машинним кодам, заголовки та правила приватності визначені лише в [моделі помилок](error-model.md). Вона також задає загальні 405, 500, 503 і однакову відповідь 404 для чужого та відсутнього бронювання. Таблиці операцій вище зберігають застосовні статуси й умови; формат тіла не дублюється.

## Закриті питання

Строк сесії, наслідки зміни пароля та Q-07 закриті [ADD-001](../spec/srs-addendum-001.md). Немає нових маршрутів, полів чи кодів; mock не виконує життєвого циклу сесій або календарних обчислень.
