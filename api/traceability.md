# Трасованість операцій REST API до SRS

Джерела: [SRS](../spec/srs.md), [функціональні вимоги](../spec/functional-requirements.md), [критерії прийняття](../spec/acceptance-criteria.md), [глосарій](../spec/glossary.md), [BDD](../spec/bdd-scenarios.md), [вимоги API](requirements.md) та [операції](operations.md). URI наведено повністю; діапазон REQ-ID включає обидві межі.

Зв’язок означає призначення операції, застосування правила або його відображення у відповіді. Допоміжні читання позначено як проєктні способи виконання вимог, а не окремі вимоги SRS. Трасованість **не підтверджує реалізацію або проходження тестів**. Зворотні зв’язки REQ → OP наведено в requirements.md.

## Результат звірки та межі

Зіставлено **22 з 22 операцій**, OP-01–OP-22, без зміни методів і URI. У зв’язках є всі **92 функціональні REQ-ID**; для кожного є зворотний запис у requirements.md. Автоматичні правила враховано на записі, читанні результату або перевірці доступності, без додаткових маршрутів.

Прогалин у зв’язках OP ↔ REQ немає. Прямої окремої вимоги на допоміжні читання OP-06, OP-14, OP-18, OP-19 SRS не формулює: їх обґрунтовано наявними вимогами керування/перегляду та позначено як проєктну деталізацію. Наявність посилання не означає, що одна операція самостійно виконує всю вимогу.

Прогалини деталізації контракту залишаються відкритими: строк сесії, наслідки зміни пароля для сесій та календарне питання Q-07 про проміжні добові межі/90-денний горизонт під час переходу часу. Трасованість їх не вирішує. Нефункціональні вимоги не входять до цієї таблиці; загальну spec/traceability-matrix.md не змінено. Реалізація та тестування цією звіркою не засвідчуються.
