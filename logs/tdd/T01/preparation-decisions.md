# T01: рішення користувача та межі підготовки

Дата: 30.10.2026. Джерело рішення: повідомлення користувача в поточній розмові «Продовжуємо підготовку REST API до реалізації через TDD». Рішення записав агент Codex; автор наведених погоджень — користувач. Цей документ не є новим функціональним адендумом.

## Зафіксовані рішення користувача

- Погоджено стек: Python, FastAPI, PostgreSQL, SQLAlchemy/psycopg, Alembic, pytest/HTTPX.
- Погоджено JSON-логування з request_id.
- Погоджено [план TDD](../../../planning/tdd-implementation-plan.md) як основу подальшої роботи; базова версія — коміт `a0a2bb04848729f6a481d4dbd3cf846c7109be2d`.
- Дозволено підготовку ізольованого backend-середовища, інфраструктури логування й тестів T01/F007. Для середовища слід вибрати сумісні версії та відтворювано зафіксувати їх; використовувати uv, якщо доступний. Наявне середовище валідації OpenAPI не змінювати.
- Для логування дозволено малий TDD-цикл: тести → фактичний RED → мінімальна реалізація → GREEN, з обов’язковою зупинкою після RED до повідомлення користувача про коміт тестів і доказів.
- Календарна бізнес-логіка заборонена на цьому етапі. Для збору й запуску тестів дозволені мінімальні інтерфейси з явним NotImplementedError; skip/xfail для приховування падінь не використовувати.
- PostgreSQL не потрібна для календарних модульних тестів. Підготувати лише конфігурацію окремої майбутньої тестової БД; не використовувати робочу БД чи SQLite як підміну PostgreSQL.
- Не виконувати git add, git commit або git push. Після кожного завершеного етапу для окремого коміту зупинитися й передати точний список файлів та запропоновану назву коміту. Не переходити від RED до реалізації відповідної поведінки до повідомлення про коміт.

Не погоджені цим повідомленням: інші функціональні пакети, конкретні версії залежностей (їх вибір доручено агенту), критерій стійкості паролів Q-09, тікетні призначення REQ-F-093–096, Validation задуму/результату, проходження TEST-GATE, G-READY або прийняття бізнес-реалізації. Публічні поля/заголовки й семантика OpenAPI не змінюються.

За [CP-08](../../../planning/revised-decomposition.md) G-PLAN потребує актуального G-SPEC і перевірених планових матеріалів; G-SPEC потребує погоджених CP-01/CP-02 для названого обсягу та людського висновку CP-06/задум. У [ролях](../../../planning/roles.md) і [залежностях](../../../planning/ticket-dependencies.md) ці рішення залишені людині.

Погодження плану як основи та прямий дозвіл на підготовчі роботи наявні в повідомленні користувача. Проте документального актуального рішення G-SPEC із його обсягом/версією та висновку людини CP-06/задум не знайдено. Тому **повне проходження G-PLAN не підтверджується**. Для завершення запису потрібні посилання на такі чинні матеріали або фактичні людські рішення; агент не пише їх замість людини. Для всього проєкту лишаються також раніше виявлені прогалини оцінок/покриття після ADD-001.

Для огляду обмеженого обсягу вже наявні: чинний [SRS](../../../spec/srs.md), [ADD-001](../../../spec/srs-addendum-001.md) із закритим Q-07, відповідні [AC](../../../spec/acceptance-criteria.md) та [BDD](../../../spec/bdd-scenarios.md), погоджений як основа план, [базова декомпозиція](../../../planning/revised-decomposition.md), [календар/оцінки](../../../planning/phased-plan.md), ролі й B/I/C-залежності. Погодження плану не перетворює старі оцінки автоматично на оцінки нової роботи. Прямий дозвіл користувача достатній для названої підготовки; відсутній запис G-SPEC не трактується як дозвіл на календарну бізнес-реалізацію.

## Послідовність окремих передач користувачу

1. **Поточна межа: рішення та обсяг.** Цей запис і посилання на нього у плані/історичному аудиті. Зупинка для окремого документаційного коміту.
2. **Середовище та мінімальний runner.** Відтворювані залежності, ізольоване середовище, мінімальна структура й конфігурація майбутньої тестової PostgreSQL, інструкція; окрема перевірка імпортів/runner без бізнес-RED. Зупинка з переліком файлів.
3. **Логування: тести й RED.** Інфраструктурні очікування, мінімальні інтерфейси, фактичний RED, команда/exit code/аналіз і безпечні докази; зупинка. Реалізація логування тільки після повідомлення користувача про коміт тестів і доказів RED.
4. **Логування: GREEN.** Мінімальні JSON-події, кореляція request_id, HTTP початок/завершення/статус/тривалість, без персональних даних і тіл; фактичні прогони та аналіз. Зупинка для окремого коміту.
5. **Календар: тести й RED, матеріали TEST-GATE.** Конкретні test ID/джерела, заглушки, працездатні імпорти/runner, фактичний бізнес-RED, аналіз кожного падіння та технічна рекомендація GO/REVISE. Зупинка. Календарна реалізація заборонена навіть після повідомлення про коміт: для неї потрібні окремий дозвіл і чинні погодження.

Усі кроки є частинами поточного доручення; межі не означають, що решта роботи скасована. Жодного add/commit/push агент не виконує. На кожній межі невиконані перевірки позначаються прямо. Інфраструктурний TDD не зараховується за календарний.

## Фактичні дії першої передачі

Перевірено `git status --short` (порожній), гілку `main`, HEAD `a0a2bb04848729f6a481d4dbd3cf846c7109be2d`. Сторонніх змін Git не виявлено; наявні середовища збережено. Повторний пошук `rg --files --hidden -g AGENTS.md -g '!.git/**'` не знайшов інструкцій; перевірені AGENTS.md у корені та предках також відсутні. Прочитано конвенцію комітів, план/аудит, ролі/залежності/передумови CP-08 і джерела календарного обсягу. Get-FileHash підтвердив наведений checksum OpenAPI.

`Get-Command uv -ErrorAction SilentlyContinue` не повернув команду в поточному PATH. Остаточний вибір засобу й версій — наступна передача; це не помилка тестів і не доказ RED. Пошуковий exit 1 за відсутності AGENTS.md не є збоєм продукту. Тести й установка залежностей у першій передачі не виконувалися; версії основних залежностей ще не вибрані, календарних тестів створено 0, RED/GREEN немає. Перевірки логування та інтеграції також ще не виконані. Жодного секрету, контакту або тіла HTTP-запиту в цей журнал не внесено.

Контроль документів виконано read-only Python-перевіркою через наявний `.venv-api-validation/Scripts/python.exe -X utf8 -`: 78 відносних Markdown-посилань трьох документів існують, SHA-256 контракту незмінний, Git index порожній; exit 0. `git diff --check` — exit 0, whitespace-помилок немає. Попередження Git про майбутнє LF→CRLF не змінює зміст джерел і не є RED. `git status --short` показує лише два оновлені Markdown-документи та новий запис цієї передачі. Жодних тестових FAIL немає, бо runner ще не запускався; ці перевірки документації не підміняють інфраструктурні чи бізнес-тести.
