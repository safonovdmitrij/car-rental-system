# Скоригована декомпозиція SRS на тікети

Дата: 6 жовтня 2026 року. Автор: агент Codex.

**Статус: скоригована пропозиція для перевірки людиною; не затверджено.** Жоден Gate не пройдено, Validation не виконано, реалізацію й тести не розпочато. [Первинна пропозиція](initial-decomposition.md) збережена без змін.

## Джерела та межі

Проаналізовано [SRS](../spec/srs.md), [функціональні вимоги](../spec/functional-requirements.md), [нефункціональні вимоги](../spec/non-functional-requirements.md), [критерії прийняття](../spec/acceptance-criteria.md), [BDD-сценарії](../spec/bdd-scenarios.md), [матрицю простежуваності](../spec/traceability-matrix.md), [межі](../spec/scope.md), [глосарій](../spec/glossary.md), [реєстр питань](../spec/open-questions.md), [задум](../spec/idea.md), [підсумок SKED](../logs/sked-dialog-summary.md), [історію конфлікту](../logs/conflict-resolution.md) та [огляд специфікації](../logs/spec-review.md).

База декомпозиції: 92 функціональні й 13 нефункціональних вимог, 105 критеріїв прийняття та 16 ключових BDD-сценаріїв. Огляд SR-001–SR-016 використано як перелік зауважень, а не як нові погоджені вимоги. Початкові «24 години» із задуму та історії конфлікту замінені погодженим календарним правилом SRS/SKED. Часовий пояс системи — Europe/Kyiv.

Не плануються оплата, документи водія, договори, фізична видача/повернення, мобільна адаптація, додаткові фільтри та сортування, підтвердження пошти, відновлення пароля через пошту, зміна пошти, email/SMS, бронювання адміністратором для клієнта, зміна авто/періоду створеного бронювання чи буфер між орендами. Не призначаються технологічний стек, API-маршрути або структура таблиць: SRS їх не встановлює.

## Корективи та типи міток

Збережено назви, ID і предметні межі T-003–T-018; усі вони мають тип Feature, включно із забезпеченням нефункціональних характеристик. T-001 отримав тип Specification, T-002 — Addendum. Додано шість керованих пакетів Test до реалізації, шість відповідних Verification після реалізації, дві Validation, дві Documentation та чотири Gate. Разом — 38 тікетів. Поділ за шарами системи не вводиться.

Використовуються лише надані мітки: **Specification, Addendum, Test, Feature, Verification, Validation, Documentation, Gate**. Specification готує уточнення; Addendum готує пропозицію доповнення перевірок без нової поведінки; Test готує тести, дані й методики; Feature реалізує; Verification перевіряє відповідність специфікації; Validation перевіряє відповідність задуму й потребам людини; Documentation фіксує простежуваність та використання; Gate є рішенням людини про перехід.

**Блокувальна залежність** має бути завершена до початку залежної роботи (якщо явно не вказано «до завершення»). **Інтеграційний зв’язок** не блокує початок Feature, але потребує обох реалізацій для остаточної спільної Verification. Немає взаємних блокувальних залежностей. Для перевірки із ще відсутньою суміжною функцією Test готує фікстури/імітації; остаточна Verification виконується на інтегрованій системі.

Q-01–Q-10 перенесені без прийняття рішень. Відкрите питання, що визначає очікувану поведінку або критерій, блокує Test та відповідну Feature; воно не відкладається лише до прийняття. Людина може дозволити обмежений, незалежний обсяг через окремий запис READY-GATE, явно залишивши залежну частину заблокованою. Нові продуктово значущі правила потребують окремого погодження; цей документ їх не встановлює.

## SDD-цикл і контрольні точки

Запропонована послідовність: VAL-001 та T-001/T-002 → SPEC-GATE → DOC-001 → PLAN-GATE → відповідний Test та проєктування Feature → READY-GATE для цієї Feature → Feature → Verification → DOC-002 та VAL-002 → ACCEPTANCE-GATE. Це план майбутньої роботи. Поточне доручення дозволяє створити лише цей документ, а не виконувати його тікети, змінювати SRS чи ухвалювати Gate.

Кожен Gate початково має статус **«очікує рішення людини»**. Агент може підготувати матеріали, але рішення, дозволений обсяг, дату й автора фіксує людина. Відсутність відповіді не означає проходження. Validation також виконує людина; проходження тестів не підміняє її оцінку задуму.

Для діапазонів ID включено обидві межі. Кожний REQ-F-NNN має AC-F-NNN-01, кожний REQ-NF-NNN — AC-NF-NNN-01. Джерела Test/Verification: [AC](../spec/acceptance-criteria.md), [BDD](../spec/bdd-scenarios.md), [SRS](../spec/srs.md) та погоджені в майбутньому уточнення. BDD охоплюють лише ключові сценарії; вимоги без BDD перевіряються за AC. Посилання на BDD не є доказом виконаної перевірки.

## Уточнення та доповнення

### T-001 — Уточнити неоднозначності специфікації

- **Тип:** Specification.
- **Опис:** отримати рішення людини щодо Q-01–Q-10 і зафіксувати їх із прив’язкою до вимог; не трактувати пропозиції огляду як погоджені правила.
- **Вимоги:** REQ-F-002, REQ-F-007, REQ-F-027–REQ-F-030, REQ-F-035–REQ-F-037, REQ-F-065–REQ-F-067, REQ-F-069, REQ-F-073–REQ-F-075, REQ-F-081; REQ-NF-001–REQ-NF-004, REQ-NF-006, REQ-NF-008–REQ-NF-009.
- **Умови завершення:** людина відповіла на всі питання; кожне рішення має джерело, пов’язані REQ/AC і перелік задач, на які впливає; узгоджено статус реєстру питань. Відкладене рішення залишається явною залежністю, а не позначається вирішеним.

- **Джерела:** [SRS §5](../spec/srs.md#5-невирішені-питання), [огляд SR-001–SR-016](../logs/spec-review.md), [первинна декомпозиція](initial-decomposition.md).
- **Блокувальні залежності:** немає; рішення людини щодо кожного Q потрібне до завершення відповідного уточнення. VAL-001 — спільне узгодження задуму.
- **Артефакт майбутньої задачі:** пропозиція уточнень/доповнень із REQ/AC та рішеннями людини. У цій роботі SRS, AC, BDD і реєстр питань не редагуються; доповнення не вважаються чинними до рішення людини.

### T-002 — Узгодити повноту приймальних перевірок і простежуваності

- **Тип:** Addendum.
- **Опис:** підготувати для перевірки людиною усунення прогалин SR-011–SR-015, не змінюючи продуктову поведінку.
- **Вимоги:** REQ-F-004, REQ-F-019–REQ-F-020, REQ-F-040–REQ-F-042, REQ-F-074, REQ-F-077, REQ-F-079, REQ-F-082–REQ-F-092.
- **Умови завершення:** погоджено перевірку конкурентного бронювання та конфліктної службової операції без збереженого перетину; скидання лічильника після блокування перевіряється без проміжного успішного входу; прямі API-перевірки охоплюють усі застосовні заборони, включно з гостем та адміністратором. Для BDD-002 і BDD-015 відрізнено передумови від перевірки обов’язковості полів; заплановано негативні перевірки AC-F-004-01 і AC-F-074-01. Нові або скориговані перевірки схвалено людиною; пріоритет переможця конкурентної операції не вигадується.

- **Джерела:** [SRS §5](../spec/srs.md#5-невирішені-питання), [огляд SR-001–SR-016](../logs/spec-review.md), [первинна декомпозиція](initial-decomposition.md).
- **Блокувальні залежності:** релевантні рішення T-001, якщо вони визначають очікуваний результат; до завершення — погодження людиною запропонованих доповнень.
- **Артефакт майбутньої задачі:** пропозиція уточнень/доповнень із REQ/AC та рішеннями людини. У цій роботі SRS, AC, BDD і реєстр питань не редагуються; доповнення не вважаються чинними до рішення людини.

## Feature: наявні групи реалізації

Спільні умови завершення Feature: реалізована описана поведінка в дозволеному READY-GATE обсязі, підготовлені тести застосовані до реалізації, результат і локальні перевірки передані до відповідної Verification. Формальну відповідність та інтеграцію підтверджують окремі VER-тікети; прийняття людиною відбувається через Validation і Gate. Проєктування входить у підготовку цієї задачі до READY-GATE і не дозволяє починати реалізацію завчасно.

- **Джерела:** [задум](../spec/idea.md), [SKED §3–§5](../logs/sked-dialog-summary.md), [межі першої версії](../spec/scope.md), [SRS §1.2 та §2](../spec/srs.md). Початкові «24 години» оцінюються з урахуванням погодженого календарного уточнення.

### VAL-002 — Валідувати реалізовану систему з людиною

- **Тип:** Validation.
- **Опис:** людина оцінює демонстрацію сценаріїв гостя, клієнта й адміністратора та придатність результату для погодженого прокату з однієї точки. Перевірка зосереджена на потребах, а не лише проходженні тестів.
- **Вимоги:** REQ-F-001–REQ-F-092, REQ-NF-001–REQ-NF-013 у контексті потреб і меж.
- **Блокувальні залежності:** VER-001–VER-006, DOC-002, висновок VAL-001.
- **Умови завершення:** збережено висновок людини, розглянуті сценарії та зауваження з прив’язкою до чинних вимог. Нові побажання не включаються автоматично в обсяг SRS; невирішені зауваження передані на ACCEPTANCE-GATE.
- **Джерела:** [задум](../spec/idea.md), [SKED](../logs/sked-dialog-summary.md), [межі](../spec/scope.md), [SRS](../spec/srs.md), [BDD](../spec/bdd-scenarios.md), висновок VAL-001 та звіти VER-001–VER-006.

### DOC-001 — Документувати план і простежуваність перед PLAN-GATE

- **Тип:** Documentation.
- **Опис:** підготувати узгоджений пакет планування: зв’язки вимог, задач, критеріїв і тестових пакетів; рішення та відкриті питання; блокувальні й інтеграційні залежності.
- **Вимоги:** REQ-F-001–REQ-F-092, REQ-NF-001–REQ-NF-013 як предмет простежуваності.
- **Блокувальні залежності:** SPEC-GATE.
- **Умови завершення:** 105/105 REQ мають Feature, Test та Verification; джерела, Q й контрольні точки доступні для перевірки; початкова пропозиція збережена. Пакет передано людині на PLAN-GATE, його статус не позначено затвердженим завчасно.
- **Джерела:** [первинний план](initial-decomposition.md), [поточний план](revised-decomposition.md), [матриця](../spec/traceability-matrix.md), [SRS](../spec/srs.md), [AC](../spec/acceptance-criteria.md), [BDD](../spec/bdd-scenarios.md). На поточному етапі матриця у spec/ не редагується.

### DOC-002 — Документувати використання, відновлення та докази відповідності

- **Тип:** Documentation.
- **Опис:** підготувати документацію фактично реалізованих операцій ролей, календарних і цінових правил, обмежень, порядку резервного копіювання/відновлення та результатів перевірок.
- **Вимоги:** REQ-F-001–REQ-F-092, REQ-NF-001–REQ-NF-013 як предмет документації.
- **Блокувальні залежності:** VER-001–VER-006 до завершення; чернетки можна готувати після відповідних Feature.
- **Умови завершення:** опис узгоджений із чинною SRS та перевіреною реалізацією; простежуються REQ → Test → Feature → Verification, версії Chrome/Edge, умови вимірювань і докази відновлення. Матеріали готові для VAL-002 та ACCEPTANCE-GATE; не описано непередбачені можливості й не заявлено прийняття людиною.
- **Джерела:** [SRS](../spec/srs.md), [глосарій](../spec/glossary.md), [межі](../spec/scope.md), [AC](../spec/acceptance-criteria.md), [матриця](../spec/traceability-matrix.md), результати VER-001–VER-006, зокрема REQ-NF-007–REQ-NF-009 щодо відновлення.
