## Як читати матрицю

| Рівень доказу | Значення |
| --- | --- |
| Документальне покриття | REQ пов’язано з описаними AC/BDD, плановими тікетами, OP та явно зазначеними в картках POS/NEG. Наявність зв’язку не підтверджує реалізації |
| Статичні відповіді mock | PASS конкретного POS/NEG підтверджує статус, тіло, схему, named example й застосовні заголовки на валідному носії з Prefer. Це не проходження REQ/AC/BDD |
| Майбутні бізнес-перевірки | Потрібні backend, ізольовані фікстури та керований час. Реальні сесії, анулювання токенів, календар, ролі, власність, конкурентність і збереження даних не перевірені |

Діапазони ID включають обидві межі. «—» у таблицях API означає **відсутність прямого задокументованого зв’язку**, а не успішне проходження чи незастосовність вимоги. Порожні старі колонки «Тест / Код / Документація» збережені як історичні місця для артефактів реалізації; наявні API-документи й mock-докази наведено окремо нижче.

## 1. Вимоги → AC, BDD та планові тікети

Збережено всі наявні AC/BDD й призначення тікетів для 105 базових вимог; додано 4 REQ та 11 AC з ADD-001 і явні зв’язки BDD-017–BDD-020. Старі тікети залишаються плановими, не виконаними. Для нових REQ-F-093–REQ-F-096 окреме призначення тікетів не знайдено: воно позначене явно й не успадковане від інших вимог. ADD-001 посилається на процес CP-01/CP-02, але це не призначення Feature/Test/Verification для нових REQ. Gate очікує рішення людини.
